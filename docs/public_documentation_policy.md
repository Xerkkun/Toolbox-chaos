# Public documentation policy

Public documentation describes the software that a user can install and run
from the current release. It must be portable, evidence-based, and usable
without access to a developer workstation or a private conversation.

## Public direct documentation

The README, installation and user guides, troubleshooting, scientific-use
guidance, packaging/distribution rules, and bundled Sprott theory are direct
documentation. They must:

- name only current controls, defaults, dependencies, and supported contracts;
- use repository-relative paths, public URLs, or user-selected locations;
- distinguish a catalog reference record from an executable runtime system;
- distinguish finite numerical evidence from proof of chaos, attraction,
  stability, or hiddenness;
- state an unavailable capability as disabled with a clear reason;
- avoid personal paths, chat text, internal prompts, review instructions,
  correction logs, completion claims, and future-work checklists.

## Historical and evidence material

`CHANGELOG.md`, `RELEASE_NOTES.md`, benchmark records, test logs, and archived
research evidence may record a version or measurement history when that is the
purpose of the artifact. They are not user instructions and must not be copied
into bundled help pages as progress tracking. Generated catalog documents must
label their finite computation and runtime-coverage fields explicitly.

## Distribution boundary

Public artifacts never include user-local Sprott dictionaries, protected book
media, private downloads, credentials, local galleries, build caches, or
developer outputs. A local permission or private preservation copy does not
change the official release whitelist, and release checks are not bypassed for
an official artifact.
